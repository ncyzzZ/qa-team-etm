# Playwright script rules (used by Claude Code here and in the Playwright repo)

Read this before writing or changing any spec. Part of the QA team knowledge (it used to be item 9a of skill `etm-nn-fullqa`). The project's own layout, fixtures, locators and app quirks are in its script notes (listed under "Knowledge" in the active project rules, `.claude/active-profile.md`): read them with this file.

**Mindset**: tests exist to FIND defects, not to turn green. The user does not want any bug to reach UAT or PROD, so look for as many real errors as possible (negative/boundary input, wrong order, two users at once, refresh, other roles, side effects, pop-ups/messages, leftover data, console and 4xx/5xx errors). Never bend a script to make it pass; when the app contradicts the TC, report what it really does and ask: TC wrong or defect.

**Playwright execution**: scripts are normally written by the automator right after the Xray push. The user runs them on the same Mac with VPN on (Claude Code can run them directly if VPN is on). Read steps with `xray_get_test_steps` (one call per Test), never via Chrome.
   - **Spec layout**: spec named by what it tests, e.g. `tests/fe/e2e/<page>/verify<Page><What>.spec.ts`. One `test()` per Xray Test, title starts with the key (`'<KEY>-7042 - <summary>'`), one `test.step('N. <action>')` per Xray step so results map 1:1 (step titles carry `Step n:` matching the pictures, including second flows). Page-object pattern: `pages/<x>Page/{locators,actions}`, getter in `pages/pages.ts` wrapped in `withStepScreenshots`, one `<role>Pages` fixture per login role (names in the project's script notes). Page ids in `.env` + `appConfig/config.ts`.
   - **Evidence**: every step calls `evidence(page, KEY, n, '<slug>', <locator>, 'Step n: <what it shows>')` from `@utils/xrayEvidence` (full-page PNG with red frame and label, saved to `evidence/<KEY>/stepN_<slug>.png`). On a login step (title or label contains "login"/"log in"/"sign in") the helper adds a badge "Logged in as: <email>" at the bottom right of the picture (waits until the page has finished loading first). The email comes from the role credentials: role fixtures register it with `registerUser(context, user)` from `@utils/xrayEvidence`; a second browser context made by hand must call `registerUser(ctx, config.getCreds('<role>').username)` too. Never print the password. Before a rerun move old images to `evidence/_old/<KEY>_<HHMM>/` (`mv -n`) so only fresh evidence is imported.
   - **Before/after proof for every data change**: any Test where import/save/edit/delete changes data needs a BEFORE and an AFTER picture of the real page that shows the data (not just a toast or DB line). In AFTER mark what changed (yellow fill + red frame on each new/different value and row) and write on the label what it was and what it is now (e.g. "POB 6 -> 7, Duration 990.00 -> 984.00, row added: ..., row gone: ..."). Snapshot page text before the action and diff after so marks are automatic (see `markChanges` / `snapWork` in `verifyImportWorkBasic.spec.ts`). Make test data so the change is visible (add, revise and delete each show). If the record is deleted and has no page, show the list where it is gone (Total Results before and after) and say so on the label. Judge each step: does the page match the file/Expected Result? A passed run with no visible before/after picture is not enough.
   - **No false pass** (checked by gate G6, measured per Sprint): a test is green only when every step was checked. A step that cannot be checked (data missing, `.env` empty, done by hand, Dev pending) calls `notChecked('<why>')` from `@fixtures/pageFixtures` (or annotates with type `partial`, `skipped-step`, `not-scripted`, `needs-manual`, `check-by-eye` or `manual`); the shared `notProvenGuard` then reports the test as skipped with the reasons. Never: `return` out of a step without that call; `.catch(() => ...)` on an action whose result an `expect` then relies on (assert the element is visible first); `.every()` / `.some()` on a list that can be empty (use a helper that fails on empty); `if (...) expect(...)` without an `else` that calls `notChecked`; a "note down" step for a rule the AC defines (only `record` / `ba-confirm` for behaviour the BA has not defined). The whole test skips with `test.skip(cond, why)` when its precondition is missing.
   - **Look vs Figma**: when `dataTests/design/<KEY>/figma-spec.json` exists, use `expectDesign` (texts and style, soft expects, from the snapshot) and `designCompare` (app picture next to the Figma picture under the step, annotation `design-look`, a person judges the layout) from `@utils/designCheck`. No pixel diff as pass/fail: real data and font rendering differ from the mockup.
   - **Assert what the Expected Result says**, including real CSS (e.g. `toHaveCSS('background-color', ...)` for a red cell).
   - **DB checks** via `queryDb` from `@utils/dbHelpers` (`.env` `DB_*`, `DB_SSL=true`, client certs in `dataTests/accessDB/`). Never print credentials.
   - **Test data**: pick rows dynamically (first editable row, a Predecessor pair from the chart's data store), compute expected values from the row's real data, avoid saving unless the TC needs it, otherwise restore in `finally`.
   - **Depth checklist** (goal: if the app is broken the test fails, if not it does not fail at random; not "assert everything"): (1) every step checks a real outcome, what should change did, what should not stayed (e.g. after editing Start, End/Duration follow the rule and neighbouring rows are unchanged), plus follow-on state (Save enabled/disabled, no stuck pop-up, no leftover red cell); (2) layers by risk: UI (text, format, CSS colour, enabled/disabled) always, data (after Save + refresh the value stays, DB matches screen, timezone) only when AC is about saving, side effects (chart bars, resource chart, dependency, critical path) when AC touches them; (3) negative checks: wrong input not accepted and not saved, view-only user gets no editor; (4) collect `console` errors and 4xx/5xx responses in a shared fixture and fail on them; (5) clean predictable data, each test runnable alone and repeatable; (6) web-first assertions (`expect(...).toHaveText`), never `waitForTimeout`, meaning-based locators (`data-id`, `data-column`, role) never screen position, bring Bryntum rows into view with `showRow` before reading (else `innerText` waits until timeout), failure messages that say what broke; (7) prefer data over pictures (e.g. Bryntum task store `critical` flag) and keep the screenshot as evidence; (8) know when to stop: do not assert every pixel or label, things only a person can judge get evidence, test by hand if automation costs more than it is worth (e.g. a Filter Panel date range picker).
   - **Security checks (extra to the Xray TCs, pick those that fit the Story)**: own spec e.g. `verify<Page><What>.security.spec.ts`, titles `'[<STORY-KEY>][Security] <what it checks>'`, tagged `@security` (run with `-g @security`). Use Playwright `request` with each role's saved login (`config.statePath('<role>')`) to call the API directly. Find the endpoint from the app (record the request the UI sends on Save via `page.waitForRequest` / `waitForResponse`) or ask for Swagger. Never guess endpoints. Check: (1) authorization: view-only role (e.g. Job Owner) calling save/update gets 403 and DB unchanged; a user without access cannot read/change an event/plan by swapping the id (IDOR); invalid token or after logout gives 401; (2) server-side validation of the Story's rules sent straight to the API (e.g. End before Start, task before Predecessor end): server rejects, DB unchanged; odd values (year 9999, impossible date, very long string, odd timezone) give a clean 4xx never 500; (3) text input: harmless XSS markers (e.g. `<img src=x onerror=window.__xss=1>`) shown as plain text and `window.__xss` stays undefined; quote/SQL-like string (`' OR 1=1 --`) saved as text or rejected cleanly, never 500; (4) data exposure: no other users' data, tokens or passwords; no stack trace, SQL or table names in errors. Safety: QA only, never UAT/PROD; small targeted requests, no scanners (e.g. OWASP ZAP), fuzzing or load without the user's explicit OK and the team told; harmless payloads; restore changed data and verify via DB. Report separately from Xray TC results. A failed security check is a defect (BE label when server-side). Create Xray Tests for them only if asked.
   - **Hand-off**: give the exact command: `PLAYWRIGHT_JSON_OUTPUT_NAME=test-results/results.json npx playwright test <spec> -g "<KEY>-xxxx|<KEY>-yyyy" --workers=1 --reporter=list,json` (never add `--headed` unless the user asks to watch; the user says so herself). When the user says the run is done ("รันเสร็จแล้ว"), build the report with `etm-evidence-report` before any new run. The user pastes back the log or screenshots.
   - **When a step fails**, decide with the user: script bug (fix the script), TC wording wrong (item 14; edit the Xray step only after the user confirms the real rule), real app bug (item 10). Don't guess. Hard-to-automate cases (browser Back + unsaved-change modal, range pickers that keep timing out): after at most two fixes, offer manual testing instead of looping; the user may set the result themselves.
   - **Push results** only with the user's go-ahead: one `xray_import_results` per Test with `status`, a short comment and `evidenceDir` = device path `<PW_REPO>/evidence/<KEY>`, once the result is final. Confirm with one narrow call (`xray_get_execution_tests`). Never send images through chat or use `addEvidenceToTestRunStep`.
   - **Defect retest by script**: add a `<KEY>-xxxx` test that replays the defect's repro steps and the linked TC, run the same way, then close per item 10.
   - **Known app quirks** (slow load, virtualised grids, confirm dialogs, VPN errors): in the project's script notes.
   - **Removing a Test from scope** (user's call): `removeTestsFromTestExecution`, `removeTestsFromTestPlan`, `removeTestsFromFolder`; the user deletes the Jira issue.

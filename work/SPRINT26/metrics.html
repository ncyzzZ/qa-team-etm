4. AI team ทำอะไรได้บ้าง

  • automation-engineer: Automation Engineer for the ETM QA team. Use after the tests are in Xray, to sort which Tests can be Playwright scripts and to write the specs, the security checks and the run command
  • ba-analyst: BA Analyst for the ETM QA team. Use first on every ETM Story, to read the Story, its acceptance criteria and QA subtasks and list what is unclear
  • evidence-reporter: Evidence Reporter for the ETM QA team. Use after the user says a Playwright run is done, to build the HTML evidence report, and for short summaries of results.
  • jira-xray-logger: Jira and Xray hands of the ETM QA team. Use only after the user's explicit go-ahead, to push tests to Xray, set up the Test Plan and Test Execution, log defects and retests, and do the closeout.
  • playwright-healer: Live step of self-healing for the ETM QA team. Use only when the FE-source lookup (tools/heal/source-lookup.mjs) found no replacement for a broken locator, the locator is a library class (Bryntum b-*, AG Grid ag-*), or a source heal failed its re-run
  • test-designer: Senior Test Designer for the ETM QA team (merged with the senior-test-designer skill). Use to design and write test cases, manual and automation-ready, from the Story, the analyst notes and the design findings
  • test-reviewer: Test Reviewer for the ETM QA team. Use after the test designer wrote a draft, to check coverage and wording and send it back when it is not good enough
  • ux-inspector: UX/UI Inspector for the ETM QA team. Use when an ETM Story has screens
  • Quality gates (tools/qa-check.mjs): ตรวจ draft TC, spec, coverage, AC strength, state.json ทุก phase · กัน test ที่ขึ้นเขียวโดยไม่ได้ตรวจ (false pass) · push ขึ้น Xray เฉพาะผลที่ผ่านในการรันจริงพร้อมรูปทุก step
  • Self-healing (tools/heal/): อ่านโค้ด FE ของ dev หา locator ที่เปลี่ยน ก่อนรันและหลัง fail · คนอนุมัติทุกครั้งก่อนแก้
  • Evidence report (tools/run-card.mjs): สร้าง report พร้อมรูปทุก step อัตโนมัติหลังรัน · แยกสาเหตุ fail (locator / data / env / assertion / flaky)
  • Human in the loop: ทุกการเขียนลง Jira / Xray / ข้อมูล QA ต้องมีคนอนุมัติบน board หรือในแชท และบันทึกไว้ใน state.json

วิธีอ่าน
  • Defect = issue type Defect (เจอใน QA) · Bug = issue type Bug (หลุดไป UAT/PROD) · นับตาม Sprint ของ defect เอง หารด้วยจำนวน Story ใน sprint นั้น (Story ที่ยกข้าม sprint นับทุก sprint)
  • กันได้ = BA แก้/เพิ่ม AC หรือ dev แก้ก่อนส่ง QA เพราะข้อที่ทีมยก · ยืนยันเดิม = BA ยืนยันพฤติกรรมเดิม ไม่นับว่ากันได้
  • ก่อน / หลัง dev = สถานะ Story ตอนที่ยกข้อนั้น · เตือนแล้วยังเกิด = defect ที่ทีมเคยเตือนไว้แต่ไม่ได้แก้
  • เติมย้อนหลัง = ข้อของการ์ดที่บันทึกหลังเหตุการณ์ (Sprint 26)
  • * = sprint ที่ยังไม่จบ ตัวเลข defect ยังไม่ครบ ห้ามเทียบกับ sprint ที่จบแล้ว
  • สิ่งที่ตัวเลขนี้ไม่ได้พิสูจน์: ความยากและขนาดงานแต่ละ sprint ต่างกัน · การเทสที่ดีขึ้นอาจทำให้ Defect ใน QA เพิ่มขึ้นในขณะที่ Bug ที่หลุดลดลง จึงแสดงทั้งสองเส้น · "-" คือไม่มีข้อมูล ไม่ใช่ศูนย์
